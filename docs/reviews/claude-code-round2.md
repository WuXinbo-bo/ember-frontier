## 1. 总体拓扑【工】

```
单人：  浏览器主线程(天工：渲染/输入/场景) ⇄ postMessage ⇄ Worker[SimCore] → 持久化端口(浏览器)
联机：  浏览器×≤4(天工)  ⇄ WebSocket ⇄ Node[SimCore] → 持久化端口(Node fs)
```

- `SimCore` 只有一份 TS 源码，不依赖 `@forgeax/engine`、DOM 或 Node 内置模块。时钟、随机数、存储、传输都从外部注入。
- **单人和联机使用同一套消息协议**：客户端发命令，核心推送状态差量。单人模式只是把传输层换成 postMessage。这样两种模式不会悄悄跑成两套规则（策划 L752）。
- 天工 ECS 只承载表现状态，是模拟状态的投影。模拟实体 ID 和引擎实体之间由表现层维护映射，**模拟层永远不读引擎状态**。
- `forge.json` 的稳定 GUID 用来标识内容定义，比如物品类型、配方、物种（对应策划 L1017）。世界里的实体实例 ID 由模拟核心自己分配，两者不要混用。

## 2. TS 单写者事务

### 2.1 单写者的含义

每个世界在任一时刻只有一个 `SimCore` 实例能修改状态：单人模式下是那个 Worker，联机模式下是那个 Node 进程。JS 在一个运行环境内是单线程的，这一点天然有利。真正的陷阱有两个：

1. **`await` 会切断原子性。** 事务执行到 `await` 时会让出执行权，其他回调可能在中间修改状态。
2. **同一个世界被两个写者同时打开。** 比如单人存档在两个浏览器标签页同时打开，或者两个 Node 进程挂载同一个存档。这一条在 §6.3 处理。

### 2.2 事务协议【工】

```
Command{cmdId, issuer, seatId?, clientSeq, payload}
  → dedup(issuer, clientSeq)                    // 已处理过则返回原结果
  → plan(readonly state) → Event[] | Reject      // 纯读：校验全部前置条件、预算、库存、资格
  → apply(Event[])                               // 同步、全函数：不能失败，不能 await
  → seq += n; journal.enqueue(events, durability)
  → invariants.check()  (测试与调试版本每次都跑，发布版本按日跑)
  → outbound.publish(events, holdUntil=durability)
```

具体规则：

- **事务体必须是同步函数。** 不允许 `await`，不允许做 I/O，不允许调用 `Date.now()` 或 `Math.random()`。随机数统一用注入的计数式 PRNG，键为 `(世界种子, 系统, 实体ID, 事件序号)`，第一轮 §3 的防重抽原则保持不变。
- **先规划，再应用。** 规划阶段完成所有校验，并把所有随机结果确定下来。应用阶段只执行确定好的结果，按设计不可能失败。这对应策划 L768 "以唯一事件提交"。
- **日志里记录的是"已结算的事件"（比如"造成7点伤害"），不记录"命令"。** 恢复时只重新应用这些事件，不重新计算。这样可以避开跨引擎的浮点差异：单人存档在 iOS 上跑在 JavaScriptCore，Node 跑在 V8，两边的 `Math.sin` 等超越函数不保证结果逐位相同。
- **账本一律用整数。** `Number` 能精确表示的整数上限是 2^53，无尽模式下的丧尸累计数在这个范围内绰绰有余。

### 2.3 持久化等级与屏障

| 等级 | 事件 | 处理 |
|---|---|---|
| `sync` | 死亡、日结算、席位绑定和死亡、物品销毁或跨组织转移、改造完成或失控 | **模拟进入屏障**：持久化确认之前不再推进 tick，这批事件也不发给客户端 |
| `group` | 普通物品移动、制作和施工进度、关系变化 | 合并批量提交，窗口建议 ≤1 秒 |
| `derived` | 导航和声场缓存 | 不持久化，可以重建 |

屏障是防止"杀掉进程绕过死亡"的关键（策划 L774、A13）。死亡事件写盘之前，客户端看不到这次死亡，世界也不会往前走。所以在死亡之前杀掉进程，最多回到不到1秒之前、仍然身处同一危险的时刻。这部分残余风险可以接受，但要写进风险登记。

### 2.4 失败处理

| 失败 | 处理 |
|---|---|
| 规划阶段拒绝 | 返回原因码，状态不变。客户端重发同一个 `clientSeq` 时返回同一个拒绝结果 |
| 应用阶段抛出异常（程序缺陷） | **立即停机**，世界标记为故障。从最近一次快照加日志恢复到这批事件之前，生成诊断包。**不在已被部分修改的内存状态上继续运行** |
| 发布版本的不变量审计失败 | 停机，导出诊断，禁止自动修复账本。修复工具只允许补正派生数据，不允许撤销死亡（策划 L774） |
| 持久化失败（配额不足、写入错误） | 停在屏障，界面提示。重试 N 次后保存只读诊断，不允许在没有持久化的状态下继续游戏 |
| 模拟跟不上实时 | 见 §4.4，用时间膨胀处理，不跳过逻辑 |

## 3. 可序列化状态

**硬性约束【工】：**

1. 权威状态只能是纯数据：普通对象、数组、类型化数组、字符串、整数。**不能放**类实例方法、闭包、Promise、生成器、`setTimeout` 句柄、以对象为键的 `Map`、对象之间的直接引用（一律改成 ID 引用）。
2. **一切挂起中的工作都要表示成数据：** 制作和施工进度、灾害阶段、改造进度、NPC 的 HTN 任务栈和当前计划、离散事件队列（`{dueTick, kind, payload}` 组成的优先队列）。NPC 规划器不能用 `async` 函数或生成器来保存"做到一半"的状态，因为这些无法存档。这一条最容易被违反，应该在代码评审规则和 lint 里明确禁止。
3. **明确区分权威状态和派生缓存。** 导航层级、连通分量、声场、据点保护位图都是派生数据，读档后重建。每份缓存带上它依赖的 `chunkVersion`。
4. **存档里只引用内容 GUID 的映射。** 存档头保存一张"内部紧凑索引 → GUID"的表，热点数据存紧凑索引。这样内容表调整顺序不会破坏旧存档，跨版本迁移脚本只需按 GUID 映射。
5. **布局：** 热点数据用 SoA 类型化数组（丧尸群体、区块网格），以二进制段写入；稀疏实体以记录形式写入。存档头包含 `schemaVersion`、`rulesDataHash`、`seed`、`lastSeq`、两套人口账本和 `generation`。

**自动化测试：**

- 序列化、反序列化、再序列化，结果字节一致。
- 在同一运行环境里，"继续运行 N tick"和"存档读档后运行 N tick"得到的状态哈希一致。
- 在 Node 和浏览器之间交叉加载存档，**只要求事件重放结果一致**，不要求继续模拟逐位一致。

## 4. 分层人口

### 4.1 账本与状态在同一个事务里修改

人口计数器只能在改变实体状态的同一个事务里修改。审计时必须同时满足下面四条。缓冲区的定义见 §5。

```
zombieAlive == 10000 + 10000·d − K                  【硬】L644
zombieAlive == Σcohort.count + #individuals + buffer.zombies
           == free + restrained + controlled         【硬】L1229
npcAlive    == 99 + 100·d − D                         【硬】L395
npcAlive    == #npcEntities(在图) + buffer.npcs
```

### 4.2 日结算协议

- 日结算是一个 `sync` 级事件 `DayRollover{day}`，以 `ledger_days[day]` 作为幂等键（A22）。账本数量**立即**增加，新个体全部进入"待放置"队列。
- 放置工作按每个 tick 的预算分批执行，每批都是一个独立事务。放置不成功的个体留在队列或缓冲区里，**数量不扣减**（策划 L656）。
- 读档时，未完成的放置队列从存档里恢复继续执行，**不重新触发日结算**。

### 4.3 丧尸和 NPC 分层（在第一轮基础上的修订）

- **远处权威位置就是所在的区域桶**（第一轮 §6 的约定保持不变）。这是声音判定能跨层一致的前提。
- **修订：无尽模式下，持久个体数量不能单调增长。** 只因"被看到过"而转成个体的丧尸，在没有演化、没有伤势、没有被约束或控制、身上没有物品的情况下，离开关注范围后允许并回匿名群体。真正独有的状态（演化进度、受控、改造、持有物品）才会让它永久保持个体身份。
- **NPC 三个层级使用同一个规划器**（策划 L464 的要求不变）。LOD2 层用离散事件调度。认知隔离做成类型层面的约束：规划器模块只能导入 `Belief` 接口。工程上还应加一条依赖规则，禁止 `planner/**` 导入 `world/**`，交给 lint 或依赖检查工具执行。

### 4.4 算力不足时的处理：时间膨胀，不降级规则

单写者跟不上实时节奏时，按以下顺序处理：

1. 降低表现层细节。
2. 在不影响结果的前提下，降低 LOD1/LOD2 的执行粒度，比如把移动步长放粗，但规划频率不变。
3. **全局放慢游戏时间**，比如显示"模拟 0.8×"。联机时整个世界一起放慢。所有规则按游戏时间计算，所以账本、饥饿、日增都不受影响。
4. 膨胀倍率持续低于阈值（比如 0.5×）时，提示当前设备或服务器不满足标准世界的要求。

**禁止的做法：** 跳过 NPC 规划、不交付声音事件、删除远处实体、暂停日增（策划 L829、L972）。这条失败路径应该写进验收：压力测试必须报告膨胀倍率曲线。

## 5. 无尽模式与有限地图饱和

**矛盾：** 策划 L650 要求线性增长且不封顶，L670 禁止暗中封顶；L652 要求生成在合法、不重叠的位置，L668 要求能对应到实际位置交互。地图尺寸是有限的。

**落地协议【工】：**

1. **每个区域桶设硬容量** `cap(bucket) = 可站立格数 × k`，k ≤ 1。前提是这个桶里的个体在需要时能全部无重叠地物化。超过容量的数量不能"挤"在桶里，否则交互时无法兑现 L668。
2. **迁入缓冲区**挂在实际的迁入路线上，比如图边道路入口和海上来源。日增中放不下的部分进入缓冲区：
   - 缓冲区计入世界存活数，在账本中单列。
   - 缓冲区只保存整数，存储成本不随数量增长。
   - 区域腾出容量后，沿真实路线放出（对应策划 L654、L962）。
   - 缓冲区在世界中**可以被观察到**，比如边缘尸潮的规模提示，这是策划 L711 要求的预警。
3. **缓冲区里的个体不参与模拟**：不演化、不感知、不发声。它们一进入地图，就按普通新个体处理。
4. **NPC 同样会饱和**：比如出生点全部被淹没或被据点占据。NPC 缓冲区叫"在途流民"，问题是它们在缓冲区里要不要消耗食水。我建议不消耗，入图时状态等同新人，因为策划 L393 要求新增者使用白板模板。**需要策划确认。**
5. **饱和状态要明确告诉玩家**，比如"本区域已饱和，新增转入边缘迁徙"，不要伪装成其他情况。
6. **无尽模式的长期终局**（第一轮 D20）仍需策划决定。可选方向：
   - 接受世界最终被填满，作为无尽模式的自然结局；
   - 用"慢节奏世界"预设，并明确标注改动了增长规则（策划 L962 已允许）；
   - 用阶段目标结算（策划 L146）。

   **工程层面不提供任何隐性上限。**

**需要决策：**

- **D2'：** 缓冲区是否计入存活数？我建议计入。
- **D2''：** 地图尺寸。用第一轮 §4.4 的密度表，结合 S2 基准结果来定。

## 6. 平台持久化能力尚未证实

**原则：** 不预设 OPFS、IndexedDB 配额、浏览器是否会回收存储、Node 部署环境的 fsync 和 rename 语义。全部通过运行时探测和配置来确定。

### 6.1 持久化端口

```ts
interface PersistencePort {
  probe(): Promise<Caps>;       // 只在启动阶段调用，不在事务里
  appendJournal(seg, bytes, sync: boolean): Promise<Ack>;
  writeSnapshot(slot: 'A'|'B', bytes): Promise<Ack>;
  commitManifest(m): Promise<Ack>;   // 原子切换当前快照槽位
  acquireWriterLease(worldId): Promise<Lease | Busy>;
}
type Caps = { atomicManifest, durableAppend, quotaBytes?, persistent?, exclusiveLock, p95WriteMs }
```

- **快照用 A/B 双槽，每个槽带校验和，再用 manifest 指针切换。** 这样不依赖原子 rename：如果平台支持在单个事务里原子写入，就用一次事务提交 manifest；否则写入带序号和校验和的 manifest 副本，读取时取最新的有效副本。
- **日志按段分文件，每条记录带 CRC。** 恢复时截掉尾部损坏的记录，回到最后一条有效记录。
- **死亡登记表单独存放。** 只追加，带哈希链，记录 `generation`（第一轮 §8.3）。从旧快照恢复时，必须重新应用登记表里的全部死亡。

### 6.2 启动分级（对应你说的"显式降档或阻止"）

| 探测结果 | 处理 |
|---|---|
| 持久追加、原子 manifest、独占锁、配额 ≥ 标准世界预算都满足，且写入延迟 p95 ≤ 阈值 | 允许标准大世界 |
| 缺少持久化授权（浏览器可能回收存储） | 允许启动，但长期显示提示：存档可能被浏览器清除。**清除的后果是世界丢失，不是复活** |
| 配额不足以支撑标准大世界 | 只允许明确标注的"小世界预设"，或者阻止启动 |
| 没有独占锁，或者 Worker 不可用 | **阻止启动正式世界**。不在主线程上运行一个降级版核心，避免跑成两套代码路径 |

具体阈值和"标准大世界存储预算"要由 S2 基准给出，现在不预设数字。

### 6.3 单写者租约

- **浏览器：** 优先用能力探测确认可用的独占锁机制，比如 Web Locks，可用性需要实测。没有可用锁时，在存储里写一条带心跳的租约记录。拿不到租约的标签页只能以只读方式观察，或者被拒绝打开。
- **Node：** 用独占创建的方式写锁文件，内容包括进程号、启动时间和心跳。启动时清理过期锁。只有过期锁需要人工确认才能接管，不自动抢占。
- **单人存档上传到 Node 联机（或者反过来）** 是否允许，需要决定。如果允许，迁移本身要作为一次 `sync` 事件：源端存档标记为"已迁出"并只读，防止同一个世界分叉成两份各自游玩。

### 6.4 生命周期失败

- **手机切到后台或标签页被冻结：** 在页面隐藏、页面关闭这类事件上，先刷出 group 窗口的数据，再暂停单人世界（策划 L762 规定世界无人时暂停）。被系统直接杀掉时，最多损失 ≤1 个 group 窗口，`sync` 事件不会丢。
- **联机客户端切到后台：** 等同于断线，走 §7.4 的托管规则。手机玩家会频繁遇到这种情况，D6 必须尽快拍板。

## 7. 房间席位与角色永久绑定分离

### 7.1 三个概念必须分开建模

| 概念 | 生命周期 | 存放位置 | 上限 |
|---|---|---|---|
| **连接**（Connection） | 一个 socket 或 Worker 通道 | 只在内存里 | — |
| **房间席位**（RoomSeat） | 一次运行会话 | 只在内存里 | 在线人数 ≤4【硬】L71。观战者是否占名额见 D15 |
| **角色绑定**（CharacterBinding） | 跨会话，与世界同生命周期 | 存档，事件级别为 `sync` | 每个世界 ≤4【建】L734 |

- 房主是房间席位上的一个**权限**（保存、关闭、踢人、批准绑定），不是另一条模拟路径。房主的角色和其他人一样适用死亡规则。房主死亡后仍保留管理权限，并进入观战。
- `CharacterBinding{slotId, characterId, identityPubKey, state: UNBOUND|ALIVE|DEAD, boundAtSeq}`。`DEAD` 是终态，同一个 slotId 永远不能再绑定新角色。

### 7.2 身份

- **浏览器身份：** 客户端生成密钥对，用挑战应答的方式证明身份。平台是否提供账号体系还没有核实，如果有，优先使用账号。
- **身份丢失**（清除浏览器数据、换设备）：
  - 允许房主批准把一个 `ALIVE` 角色重绑到新密钥。这是 `sync` 事件，进入审计。
  - **`DEAD` 角色永远不能重绑或转生。**
- **一个绑定同时只允许一条有效连接。** 第二条连接到达时，旧连接被顶替并收到通知，避免两个人同时操控一个角色。

### 7.3 防绕过的边界与残余风险

- 已经有 `DEAD` 绑定的身份，不能在同一个世界再绑定新的 slot。
- 但新建一把密钥没有成本，所以"死亡玩家换一把密钥去占用空闲 slot"无法从根本上阻止。**可以保证的是每个世界总共最多4条命。** 中途新绑定 slot 需要房主批准，并在界面上显示该 slot 是"新角色"。这条残余风险要写清楚，不能宣称已经杜绝。
- 单人模式使用同一套模型，只是 slot 数为1。

### 7.4 重连协议

```
C→S hello{worldId, pubKey, lastAckSeq, clientBuild}
S: verify sig → find binding
   none     → 若有 UNBOUND 且房主批准 → bind(sync) → 白板模板入场
   ALIVE+LINGERING → 恢复控制
   ALIVE+STASHED   → 入场规则（出生点被敌人占据时：在相邻合法位置入场并给出入场保护提示，或排队等待；不能瞬移、不能贴脸，需拍板）
   DEAD     → 只读观战，不得到新背包或生命（A13）
S→C snapshot(关注区域, chunkVersions, 待追加的事件) → 之后发差量
```

`clientBuild` 与 `rulesDataHash` 不匹配时，拒绝进入，不在规则不一致的情况下联机。

### 7.5 失败处理

| 情况 | 处理 |
|---|---|
| 第5个连接 | 拒绝，返回"房间已满"（A12） |
| 房主断线 | 策划 L764：保存并结束会话。所有活着的角色转为 `STASHED`，这个转换要能在存档里看到 |
| Node 进程崩溃 | 重启后从快照加日志恢复，世界保持暂停，直到原在线玩家重连或超时 |
| 托管期间死亡 | 结论取决于 D6。第一轮推荐的方案C不变 |

## 8. 声音必听（TS 落地细节）

- **声场计算：** 在 `Int16Array` 或 `Float32Array` 网格上做有预算的 Dijkstra，只用一个可复用的堆，避免每次分配。同一个 tick 里同一声源的多个事件合并计算。半径上限按设计值确定，最大约150格以上，作为基准测试项。
- **交付必须完整：**
  - 在场范围内的个体丧尸，加上代表点落在场内的区域桶，全部收到事件。
  - **不允许用截断计算来节省算力。** 截断会漏听，违反【硬】L602。
  - 用"更大的直线圆"代替路径计算也不行，那等于隔墙传声，违反 A03。
- **算力不够时：** 声音事件进入积压队列，并规定最大交付延迟。
  - 近处丧尸必须在同一 tick 交付。
  - 区域桶层级允许延迟 ≤K 个 tick，K 由基准确定。
  - 积压超过上限时触发 §4.4 的时间膨胀，**绝不丢弃事件**。
- **防止重复处理：** 每只丧尸或每个桶记录 `lastSoundSeq`，同一事件不会处理两次。层级切换也是带序号的事件，声音不会在切换的间隙丢失。
- **远处 NPC 的活动也要发声：** LOD2 的活动要发出"活动噪声摘要"（第一轮 §6 第4点）。
- **测试版本内置对照检查：** 每个声音事件都用暴力遍历算一遍应接收集合，与实际交付比较，不一致时停机并输出诊断（对应 A02、A03、A86）。

## 9. 只能用基准测试回答的问题

下表不是结论，而是判断 TS 核心是否达标的测试项。

| 编号 | 测试内容 | 要记录的数据 |
|---|---|---|
| B1 | Worker 和 Node 中各跑100个游戏日，规模约101万丧尸、约1万 NPC（LOD2） | 每 tick 耗时的 p50/p95/p99、GC 停顿、堆内存、时间膨胀倍率 |
| B2 | 日结算与分批放置，含饱和后进入缓冲区的情况 | 单批耗时、放置完成需要的游戏时间 |
| B3 | 声场计算，半径5/40/120/150，室内和室外 | 单次耗时，以及积压时的交付延迟 |
| B4 | 快照序列化与写入，在各目标平台上 | 体积、耗时、`sync` 屏障的写入延迟 p95 |
| B5 | 4人分散在4个岛，地形变化后导航重建 | 重建耗时，以及计划失效通知的数量 |

**WASM 的引入条件：** 只有当某个热点在 B 系列里被实测证明不达标，并且已经做过算法和数据布局优化之后，才把这个热点替换成 WASM。替换后的模块必须是纯函数，输入输出都是类型化数组，**不持有权威状态**，这样不会破坏单写者模型和序列化。
