# 第三轮审查：《游戏底层架构方案 v1.0》

## 结论

**可以开始 P0，但开工前要先补 3 处协议定义（下面的 P1–P3），并补上 2 份缺失的配套文档。** 主方案已经采纳了你点出的 5 个方向：

- 生产身份用平台 SDK（§16.2）
- 不预设服务端存储一定持久（§17.4）
- 必听不能用桶中心点代替（§10.2）
- 缓冲人口不能冒充真实人口（§7.3）
- 事务顺序是"候选写集 → 持久提交 → 发布"（§6.1）

剩下的问题集中在三处：TS 单写者在等待存储确认时世界怎么推进；群体成员在哪个位置要能算出来；房间进程的生命周期和"跨会话的长期世界"能不能对上。

## 一、最高优先级（P0 开工前补齐）

### P1. 等待持久提交期间，模拟是否继续推进（§6.1、§6.2、§6.3）

**问题：**

- §6.1 规定了"不变量检查 → 持久提交 → 发布"的顺序。
- §6.2 允许"按 tick 或微批次提交"，又说"尚未提交的候选写集不覆盖上个已提交世界"。
- 但全文没有说明：异步写存储还没返回时，下一个 tick 能不能在未提交的状态上继续算。
  - 如果能继续，提交失败时要回滚多个 tick，文档没有给出回滚机制。
  - 如果不能继续，存储延迟会直接变成模拟停顿。

**修正：** 在 §6 补一段"推测窗口"协议。

- 每个事务在内存里保留撤销日志。允许最多 K 个 tick 在未确认状态上推进，K 由基准测试确定。
- 只向客户端发布 `committedSeq` 以内的结果。客户端自己的移动和开火表现可以照常预测。
- 提交失败时，用撤销日志把状态回退到 `committedSeq`，然后进入 `PersistenceDegraded`，世界暂停。
- 未确认的 tick 数超过 K 时，模拟在屏障前等待，不再往前推进。
- 推测窗口内，被别人打中扣血这类事件也要等提交确认后才发布。这会让表现延迟增加大约一次存储往返的时间，要列入基准测试 B4。

### P2. 群体成员的位置要能计算（§10.2、§9.3）

**问题：** §10.2 要求必听判定做到"零漏报、零多报"，部分覆盖时"拆分细胞或成员子集"。但群体只存了"细胞 + 成员区间"，没有定义每个成员在细胞里的具体位置。声音边界切过一个细胞时，哪些成员在边界内是无法判定的。

**修正：** 在 §9.3 定义成员位置函数：

```
pos(memberId, cellId, cohortRevision) → 细胞内可站立格
```

- 它是确定性的纯函数，同一细胞内的成员不重叠，细胞容量 ≤ 可站立格数。
- 必听判定、群体转个体（`MaterializeExisting`）、调试展开三处都使用这同一个函数。
- 成员的基础属性同样定义为 `f(seed, memberId)`，只存与之不同的例外。
  - 这样"保留成员 ID 区间、不保存全量对象"才真正成立。
  - 也不存在"重新抽取属性"的可能。

成员区间反复拆分合并后会碎片化，§9.1 需要补充区间集合的表示方式和碎片上限，并做测试。

### P3. 房间进程生命周期与长期世界不匹配（§16.2、§16.4、§16.5、§17.4）

插件合同里的几条规定：

- 最后一名成员离开，或宽限期到期 → "room destroyed immediately / stop"
- 运行时实例被替换 → 恢复连接会被拒绝，"never falls back to fresh admission"
- 每个房间一个后端进程，预览热重载会销毁房间

**冲突：** §16.2 写的是"跨房间重建与重连保存"，§16.5 写的是"普通离房按持久席位处理"。这两条都依赖服务端持久存储，而这一点尚未证实（§17.4 自己也承认）。

**修正：**

1. 把 §16.2、§16.5 中"跨房间"的表述改为"以 §17.4 验证通过为前提"。验证通过前，联机世界一律标注为**会话级试验**：房间销毁，世界即结束。
2. 新增"房间如何装载世界"协议：
   - 由谁指定 `worldId`。`metadata` 不能用：它是公开的、约 16 KiB 的展示字段。create 请求体里的 `data` 也不能用：它只给 agentic_mate。
   - 用 `runPreparation` 装载世界。
   - 用外部写者租约防止同一个世界被两个房间同时打开。
3. 在 §17.4 第 3 项加一条验证：`stop()` 是否保证在房间销毁前执行完毕、有多少时间可以刷盘。不能假设进程退出前一定写完。

## 三、承诺与表述需要收紧的地方

- **§13.2 第 7 条、§17.3：** 主方案说保存成功"不等价于断电下 100% 落盘"，这一句准确。但 §2 INV-07 写的是"不可复活"，没有加限定。应改为"在已提交的范围内不可逆；本地存档可以被用户回滚，属于信任边界"。
- **§22.1：** "默认最多 12 个玩家直属主动随行单位"来自 GDD 的建议值（D），应加上 D 标签。
- **§3.3、§21：** 版本号和目录结构都写成"以安装时为准"，这样写合理，可以保留。

## 五、仍需决策的事项

**产品决策：**

1. 无尽模式在有限地图上饱和后怎么办：扩展边界、明确容量后结束或迁移，还是用慢增长预设。这和 GDD L670"标准设定保留增长"的冲突需要定案。
2. 允许的最长入图延迟 `maxIngressDelay`，以及超过后 `WorldCapacityBlocked` 状态下游戏层面的表现（暂停、结算还是提示）。
3. 断线托管期间角色能否被既有威胁杀死。
4. 房主离开的语义：GDD L764 和主方案 §16.5 二选一。
5. 感染动物是否计入 10000 的丧尸账本；丧尸能否涉水、游泳，会不会溺亡。
6. 联机世界是否只允许私密、邀请制房间；新身份绑定空席位是否需要房主批准。
7. 单人模式在 Worker 不可用时：阻止启动，还是只开放小世界。

**平台验证（集中在 §17.4，补充以下各项）：**

1. 服务端可以使用的持久存储：原子性、条件写或租约、配额、吞吐，以及进程被杀、宿主重新分配后的恢复。
2. 房间销毁前 `stop()` 是否保证执行，有多少时间可以刷盘。
3. 宽限期的真实取值（30 秒还是 300 秒），以及原生宿主前后台恢复的行为。
4. 怎样把 `worldId` 安全地传给新房间，同时不走公开的 `metadata`。
5. iframe 或 WebView 里 Worker、IndexedDB 的可用性、配额和清理策略，覆盖 PC Web、移动 Web 和原生宿主。
6. 平台 `userId` 在跨设备、重装后是否保持稳定。
7. `onCheckJoin` 在 2.5 秒预算内能拿到哪些数据。
8. `storage` 云存档的单键大小上限和写入频率限制（只作为导出和备份用途）。
