## 1. 结论先行：五个决定架构的风险

1. **人口线性无上限增长，地图却是有限的。** 按 L650、L395 的公式，不计击杀时：
   - 丧尸：第30日约31万，第100日约101万。
   - NPC：第30日3099名，第100日10099名。
   - 策划禁止暗中封顶（L670），禁止删除远处丧尸（L829），无效生成点也不能扣减每日数量（L656）。
   - 但"合法、可站立且不重叠"（L652）的位置有限。所以地图尺寸、迁入缓冲区和地图饱和后怎么办，必须在 M0 之前定下来，否则人口账本迟早会和"合法位置"这条规则冲突。
2. **"必听"规则（L602）和远处的群体简化表示（L662–666）天然矛盾。** 远处群体只记录"区域里有多少只"，没有精确坐标。必须先给出一个所有层级共用的"是否在范围内"的判定，否则同一只丧尸在不同表示下可能一次听到、一次没听到。
3. **高智能 NPC 到了几千名的规模，不能在 GDScript 里做。** 计划完整性不能降级（L464）。粗估第30日每秒约250次规划，这需要原生代码的模拟核心，并在架构层面隔离"NPC 的认知"和"世界真相"（L462）。
4. **单人模式要在手机上跑完整人口模拟，是平台层面的决策。** L7 和 L801 要求支持手机，但策划没有说手机单人是否在本机运行完整模拟。这一点直接决定核心语言、内存预算和地图尺寸。
5. **永久死亡和断线之间有一处策划内部矛盾。** L760 要求断线后角色继续留在世界里托管，防止断线逃跑；L746 又说"网络断线不应作为死亡来源"。两者不能同时完全满足，需要拍板。

## 3. 推荐总体架构【工】

```
┌───────────── 客户端（Godot 4，只做表现，无权威） ────────────┐
│ 等距渲染 · 输入 · UI · 自身移动预测 · 插值 · 区块缓存          │
└──────────────▲───────────────────────────┬──────────────────┘
               │ 快照/差量（按关注区域）      │ 命令（带请求ID）
┌──────────────┴───────────────────────────▼──────────────────┐
│ 传输抽象层：ENet（原生）| WebSocket/WebRTC（浏览器）L803       │
├─────────────────────────────────────────────────────────────┤
│ 权威模拟核心 SimCore（原生语言，不依赖引擎，可无界面运行）       │
│  命令 → 校验 → 领域事件(唯一ID) → 应用 → 预写日志 → 订阅者       │
│  ├ 时间/日结算（幂等）  ├ 生成服务（唯一入口）                   │
│  ├ 地形/水文/结构       ├ 导航（分层，带版本）                   │
│  ├ 声学                ├ 人口：丧尸分层 / NPC 分层               │
│  ├ 认知(信念) / 规划 / 执行 ├ 组织 / 任务 / 预留账本              │
│  ├ 物品账本 / 制作 / 建造   ├ 战斗 / 弹药 / 载具                 │
│  ├ 随行（宠物+改造体）  ├ 研究 / 演化 / 天气灾害                  │
│  └ 持久化（SQLite + 预写日志 + 快照）· 不变量审计器               │
├─────────────────────────────────────────────────────────────┤
│ 数据表（稳定ID，L1017）：技能/物品/配方/建筑/物种/演化/声音/灾害   │
└─────────────────────────────────────────────────────────────┘
```

**关键取舍：**

1. **模拟核心和引擎分离，用原生语言（推荐 Rust 或 C++）。**
   - 单人或房主模式下，通过 GDExtension 嵌入 Godot 运行；专用服务器则独立进程无界面运行。
   - 理由一：NPC 规划和百万级群体的计算量。
   - 理由二：可以无界面做长时间压力测试，L825 要求的就是这种测试。
   - 理由三：同一份代码同时服务专用服务器。
   - 代价：GDExtension 的跨平台构建（Android/iOS，以及浏览器端 wasm）工程量大。
   - 备选是 C#/.NET，但 Godot 4 的 C# 在浏览器导出上长期受限，需要按当时的版本核实。
   - GDScript 只放在表现层。
2. **服务器权威加状态同步，不用帧同步（lockstep）。**
   - 4人可能分散在不同岛屿，客户端又包括浏览器和手机，帧同步不现实。
   - 客户端不需要和服务器逐位一致，可以避开跨平台浮点数一致性的问题。
   - 世界生成可复现（A43）只要求服务器上可复现。客户端区块由服务器下发（种子生成结果加差量），客户端按"区块哈希加版本"缓存。
3. **但核心内部要尽量确定。** 固定时间步、分系统的 RNG 流、账本全部用整数。这样就能用"快照加日志重放"做崩溃恢复和测试复现。
4. **所有状态变化都必须走"命令 → 事件"。** L768 要求"以唯一事件提交"，就靠这一条保证。客户端命令带请求 ID，服务器去重。

**防重抽原则（横跨所有系统）【工】：** 所有随机结算都用基于稳定键的随机数，例如 `hash(世界种子, 系统, 实体ID, 事件序号)`，并在**首次结算时持久化**。适用范围包括：

- 容器战利品（第一次被打开时生成，NPC 远程打开也算）
- 演化分支
- 改造能力保留方案（L1196）
- 灾害阶段
- 性格生成

这是 L680、L1196、A53、A90 共同要求"读档不重抽"的统一做法。

## 4. 人口守恒与分层模拟

### 4.1 日结算

- **【硬】时间点：** "每经过一个完整游戏日，在下一日开始时"（L393, L642）。
- **【工】日编号约定：** 开局为第1日；第 n 日结束时 d = n。这与 A05、A21 的例子一致，应在文档里写成定义。
- **【工】幂等：** `DayRollover(dayIndex)` 是一个原子事务：
  - 写入一条主键为 dayIndex 的记录；
  - 账本加10000只丧尸、加100名 NPC；
  - 所有新个体先进入"待放置"状态。
  - 账本数量立即生效，**物理放置可以分摊到后续若干 tick**。这样不会出现单帧放置1万个对象的卡顿，L762 和 A22 也不会受影响。
- **待决：** "下一日开始"指 00:00 还是黎明？如果是午夜，等于把新增人口压进夜间；如果是黎明，体验不同。

### 4.2 丧尸三层表示【工】

GDD 已经给出近、中、远三层（L662–666）。工程上建议把"身份"按需物化：

| 层 | 表示 | 身份 |
|---|---|---|
| 近（L0） | 完整个体，有碰撞、感知、伤势、战利品 | 持久实体 ID |
| 中（L1） | 简化个体，用群体流场移动 | 持久实体 ID |
| 远（L2） | 群体记录：区域桶 × 物种 × 演化特征组合 × 阶段 → 数量 + 伤势分档直方图 + 压力累计 + 目标 | 群体级身份 |

**规则：**

- 一只丧尸一旦"出现分化"，就转为持久个体，**永不再并回匿名群体**。出现分化包括：有演化进度、被捕获或约束、被玩家观察并标记、受控、带有特殊伤势。这满足 L680"按对应身份继续"和 L695"原个体"的要求。
- 群体转个体时，从直方图里抽取伤势，并扣减对应的分档；个体转群体时，并回对应分档。这是 L668"数量、伤势与类别守恒"的落地方式。
- 远处群体沿**区域级导航图**迁移，迁移受容量约束；攻城就是群体沿真实边进入（L656, L713）。

**待决（D3）：** 一只从未被观察、也没有分化的远处丧尸，能否只作为"群体中的可替换成员"存在，没有独立 ID？如果策划坚持每只都要有永久个体 ID：

- 第100日约101万条记录，每条64–128字节，合计约64–128MB。
- PC 服务器可以接受，手机单人很吃力。

### 4.3 NPC 分层："执行精度可降，意图完整性不降"

L464 是这一节的核心约束：远处可以降低频率，但不能降低计划完整性。

| 层 | 感知 | 规划 | 执行 |
|---|---|---|---|
| LOD0（玩家附近） | 实时 | 完整规划器 | 逐 tick 移动、动画、战斗 |
| LOD1（中距离） | 降低频率 | **同一个规划器** | 在区域图上粗粒度移动 |
| LOD2（远处） | 事件驱动 | **同一个规划器** | 离散事件调度：把活动排成"开始到完成"的时间段，完成时按同一份账本结算物资、工时和声音；遭遇战交给抽象战斗结算器 |

**推荐的 AI 结构：**

- **目标选择：** 效用 AI（Utility AI），权重来自需求加性格（L419）。
- **计划分解：** HTN 层级任务网络，比 GOAP 更好调试，也更适合"先满足生活再发展"的层级（L449）。
- **组织层：** 领袖规划器把目标分解为任务板（L441）。
- **记忆：** 情景记忆按重要性衰减，设上限；关系表用稀疏存储。

**认知隔离（L462 的硬落地）：**

- 规划器只能拿到一个 `Belief` 接口，包括自身观察、记忆、组织共享情报，以及带版本的地图知识（L195）。
- 规划器**在编译期就拿不到 `World` 句柄**。
- 远处模拟最容易在这里"偷看真相"：比如直接用真实库存或真实地形做寻路。所以这条必须在接口层强制，不能只靠代码评审。

**算力粗估【工】：**

- 第30日约3100名 NPC。
- 一个游戏分钟约等于1.25秒现实时间（按1440游戏分钟对应30分钟现实时间）。
- 假设平均每10个游戏分钟重新规划一次，约每秒250次规划。
- 原生代码每次约1毫秒，约占一个核的25%；GDScript 慢一到两个数量级，不可行。
- 规划在工作线程上读取快照执行，结果以命令形式提交回主循环串行应用。

**不推荐把 LLM 放进权威模拟循环。** 原因：不确定、有延迟和成本、规模达数千、需要离线和手机运行。如果将来使用，只用于对话表现，输出必须是受规则校验的结构化意图（D13）。

### 4.4 地图饱和：最容易被遗漏的边界

L656 要求无效生成点改到外部合法位置，且不扣减每日数量。但地图满了以后"外部合法位置"可能根本不存在：被淹没、全被据点占满，或者密度太高。

**密度示例（不计击杀，按总格数算，陆地占比更低时更挤）：**

| 地图 | 第30日（31万） | 第100日（101万） |
|---|---|---|
| 1024²（105万格） | 约每3.4格1只 | 约每格1只，物理上已饱和 |
| 2048²（419万格） | 约每13.5格1只 | 约每4格1只 |
| 4096²（1680万格） | 约每54格1只 | 约每17格1只 |

在2048²的地图上，第30日一个普通步行声音半径（5格，约78格面积）内平均就有约6只丧尸。

**建议【工】：** 增加一个"迁入缓冲区"状态，包括地图外的集结区和迁入路线队列。

- 缓冲区里的丧尸计入世界存活数，账本里用独立一项列出。
- 有合法位置时，沿真实迁入路线进入地图。
- 这和 L654、L962"先在远处汇聚并沿道路迁徙"一致。

**需要策划确认（D2）：**

1. 缓冲区里的个体是否算"世界存活数"的一部分？
2. 地图尺寸必须对照这条密度曲线决定。
3. 无尽模式（L146）下长期饱和的结局如何呈现。

### 4.5 两处账本歧义（需确认）

- **D4：** "丧尸动物"是否计入10000的丧尸账本？L589 把丧尸动物和人形丧尸统一归为感染阵营，L1141 也允许改造丧尸动物，但 L642、L644 只写了"丧尸"。变异动物和植物显然另有来源，需要单独的账本，否则 L658 说的"偷偷改变公式"就会发生。
- **失控体归属：** 按 L1229，失控体计入"自由"状态，这一点没有歧义，但需要在代码的状态枚举里明确写出来。

## 5. 动态地貌、洪水、岛屿与导航一致性

### 5.1 地形分层数据【工】

区块（建议32×32格）里每格记录：

- 基底标高（int16，单位分米）
- 地表材质、积雪/冰、泥泞/湿滑、盐度/污染
- 水面高度（以及流向，仅在活跃区记录）
- 承载能力

建筑、道路、桥梁是**结构实体**，有独立 ID 和结构状态（L181, L385）。

每个区块带 `terrainVersion`，长期变化以**带版本的差量**持久化（L817）。基底由种子生成，不需要存储。

### 5.2 水文：分档精度，不做全局流体（L185 允许）

| 情形 | 模型 |
|---|---|
| 活跃区内的暴雨积水 | 虚拟管道或元胞水流，约1Hz |
| 远处积水 | 预先计算的集水盆地图（盆地加溢出点），只计算各盆地水位 |
| 海啸 | 脚本化的波前和多次浪涌，每个阶段对照标高算出淹没区域；临时淹没和长期标高变化分开结算（L191） |
| 长期变化 | 侵蚀、沉降直接写入标高差量；海平面是全局常量（如需潮汐另定） |

### 5.3 导航一致性原则

**核心原则【工】：** 局部移动始终按"当前原始格子状态"做合法性校验；抽象导航图过时，只会让计划不够优，**永远不会导致非法移动**。这是满足 L185"不能沿隐形旧路行走"最稳的办法：

- 导航按移动类别分开：步行、涉水、游泳、陆行车辆、船、两栖、大型坐骑、丧尸攀爬。每类有独立的通行代价函数。
- 分层寻路：区块内部区域划分（HPA*）、区块间抽象图、按移动类别的**连通分量标签**（用于判断是否成为岛屿，L193）。
- 地形变化时：
  1. 标记脏区块；
  2. 重建这些区块的局部区域和抽象边；
  3. 在抽象图上重算受影响的连通分量（抽象图规模小，可以直接重算）；
  4. `navEpoch++`。
- 每个计划、任务、路径记录它依赖的区块版本，系统维护"区块 → 依赖它的计划"的索引。版本变化时，只推送失效通知给受影响者，由对方重新规划或报告（L209, L443, A51, A56）。
- 重建完成前，受影响区域走保守的局部 A*，直接在原始格子上搜索。

### 5.4 容易遗漏的边界

1. **实体所在格子突然变成深水或塌陷时怎么结算。** 要明确：触发涉水、游泳、溺水，结构伤害，按规则移动到相邻合法格并有可见表现。不能静默瞬移（L770）。
2. **丧尸与水（D5）。** 策划没有写丧尸会不会游泳、溺水、涉水。这直接决定岛屿能不能成为"隔离防御优势"（L988），也决定洪水是否计入环境击杀（L1233, A59）。
3. **漂移和沉没的物品、遗物。** L213 要求不能删除。需要"淹没中、可打捞"和"已掩埋、需挖掘"两种状态。如果遗物永久沉入深海，必须有获取手段（比如潜水或打捞），否则"全部可拾取"实际上落空。
4. **地图边缘全是海时日增 NPC 从哪来。** L393 说的"进入路线"如果被海隔断，需要定义水路进入或缓冲区。
5. **地形改变据点保护区。** 墙塌了，保护区缩小；新墙圈进了已有的丧尸，不能确认占据（A24）。保护区要按"建成结构 + 管理锚点 + 连通的围合区域"重新计算，用区块位图存储，生成时 O(1) 查询。
6. **声音传播要读同一份地形。** 水面、断桥、塌陷都会改变声学路径。

### 5.5 地图知识的新旧

- 每个组织保存一份"区块 → 最后看到的版本和摘要"，个人只额外保存与组织不同的部分。按 NPC 个人全量存储，第100日一万名 NPC 乘以区块数会爆。
- 侦察和交流更新这份知识（L195）。规划只读这份知识，执行时发现与现实不符再重新规划。

## 6. 声音"必听"规则

**【硬】规则（L599–605）：**

- 所有有声动作都产生声音事件。
- 有效范围内的丧尸必定接收。
- 丧尸前往声源发生时的位置。
- 传播距离有限、按路径衰减。
- 系统音量不影响结算，不读取麦克风。

**推荐实现【工】：**

1. **声音事件**包含：声源位置、时间、基础强度、是否连续、来源实体。连续声源（如发电机）按固定间隔重复发出脉冲事件。
2. **传播**：在声学网格（1–2格）上做有预算上限的 Dijkstra 搜索，代价考虑材质、门窗开合状态、天气和风向；得到一张"剩余强度场"。半径120格时约4.5万个格子，单次计算可以接受。同一声源在同一 tick 的多次脉冲合并计算。
3. **接收判定基准（关键）：**
   - 在场里剩余强度大于0的格子上的个体丧尸，**必定**加入事件。
   - 远处群体按区域桶判定：桶的代表点在场内，就是桶内全部成员接收。
   - 对外明确宣布：**远处丧尸的权威位置就是它所在的桶**，群体转个体时只放置在桶内。这样不同层级对"是否在范围内"永远一致。
4. **远处 NPC 也必须发声。** LOD2 的活动（施工2小时、砍树等）要生成"活动噪声摘要事件"，作用于周围的群体。这一点极易遗漏：远处 NPC 如果"无声干活"，就违反了 L601。
5. **事件和层级切换严格按时间顺序处理。** 层级切换本身是事件，声音不能在切换的缝隙里丢失。
6. **测试版本内置暴力遍历对照。** 每个声音事件都用暴力遍历全部丧尸算出应接收集合，和实际接收集合比较，直接用于 A02 和 A86。
7. **"已接收但继续撕咬"要有可见反馈**，比如进入警觉状态（L626）。

## 7. 高智能 NPC 验收的工程化

L464 和 §19 列出了可重复验收的场景。建议【工】：

- 每个 NPC 保存"决策轨迹"：目标、计划、失败原因、重新规划的理由。这直接用于 A30–A32，也用于调试。
- 用**场景化回归测试**：固定种子，跑断粮、缺料、阻路、尸群来袭、灾害预警，无界面运行，断言 NPC 的行为结果。
- 层级切换一致性测试（A32）：同一个 NPC 分别全程用 LOD0 和全程用 LOD2 跑同一天，比较库存、计划进度、关系的差异。允许统计意义上的偏差，不允许违反账本。
- **抽象战斗结算（D12）：** 远处战斗用同一套属性和弹药账本做统计结算，结果会和实时战斗略有不同。需要策划接受"规则一致、过程近似"。

## 8. 最多4人权威联机、永久死亡与重连防绕过

### 8.1 席位状态机【工】（基于 L734 的【建】）

```
UNBOUND ──join──▶ ALIVE_ONLINE ◀──reconnect── ALIVE_LINGERING
                     │   ▲                         │ (安全条件满足/超时)
                     │   └──reconnect── ALIVE_STASHED ◀┘
                     └──HP=0（任何活着状态）──▶ DEAD_SPECTATOR（终态）
```

- 每个世界最多4个席位，席位绑定玩家身份（平台账号，或客户端生成的密钥对）。席位一旦死亡，本局永久不可用。
- 准入：**在线连接数（包括观战者）不超过4**（A12）。旁观好友算不算名额、能不能进入，需要决定（D15）。
- 用小号占用一个未绑定席位是绕不过去的。但席位总数固定为4，所以一局最多4条命，风险可控。

### 8.2 断线托管：需要拍板（D6）

- **方案A：** 断线后身体留在世界里，由 AI 防御并主动撤退；托管期间可以死亡。防逃跑最强，但和 L746 冲突。
- **方案B：** 托管期间不受伤，但会被丧尸围住，也不能离开。这本身就是一种"无敌冻结"漏洞，可以被利用。
- **方案C（推荐）：** 区分主动退出和非自愿断线。
  - 主动退出：必须满足安全条件（附近没有敌对目标、T 秒内没有受伤、不在战斗中），否则按方案A处理。
  - 非自愿断线：短时间内按方案A托管，并在服务器端记录网络证据。
  - 同时在 UI 上明确告知规则（L760 已要求）。

### 8.3 其他防绕过要点

1. **日志持续写入（每1–2秒提交一次），死亡、日结算、物品销毁立即提交。** 否则房主可以在自动存档之前杀掉进程，回滚到不利事件发生之前。
2. **单一存档槽（铁人模式）。** 不提供"读取旧档"。备份只用于修复损坏；从备份恢复时，必须重放日志到最新的提交点。
3. **独立的"死亡登记表"。** 一个只追加、带哈希链的小文件，和主存档分开保存。即使从旧快照恢复，也会重新应用所有死亡（L774）。可选的云端登记属于 D10。
4. **本地复制存档目录无法从根本上阻止**（L774 已承认）。工程上只能做到"可检测"，不能做到"不可能"。需要决定防篡改做到什么程度。
5. **崩溃恢复后的宽限期。** 如果整个会话因房主崩溃而中断，恢复后世界保持暂停，直到之前在线的玩家重新连入或超时，避免"读档瞬间被咬"。
6. **房主本人死亡。** 房主变成观战者但仍是服务器；房主一离开，会话就结束（L764）。存活队友因此会被"卡住"。如果允许把存档转交给其他人，又会打开复制存档的漏洞（D9）。专用服务器是根本解法。
7. **零玩家时的专用服务器（D8）。** L762 写的是"没有玩家连接**且**服务器停止运行时"暂停。那么服务器在运行但没有玩家时，时间要不要走？建议默认同样暂停，持续在线另设模式。
8. **单人模式能否暂停（D11）**，策划没有写。
9. **加速时间（L144）。** 远处模拟必须能以 N 倍速追上进度，需要设定加速倍率上限。用离散事件调度可以让这一点成本很低。
10. **"离线角色"的状态。** 处于 STASHED 状态的角色从模拟中移除并冻结，不会饥饿。重新上线时，出现点被敌人占据怎么办？既不能瞬移，也不能贴脸，需要给出规则。

### 8.4 网络同步

- 自身移动做客户端预测并由服务器纠正；其他实体用插值。
- 近战和射击命中做有限窗口的延迟补偿（约150毫秒），这是 L769 的测试重点。
- 按关注区域同步。4人分处4个岛时，就是4个 LOD0 活跃区，服务器负载按此估算。
- **手机作为联机房主不建议支持**；手机只做客户端，浏览器同理（L803）。

## 9. 宠物与受控感染体的统一随行模型

用一个统一的 `Companion` 组件，挂在独立实体上：

- `controllerId`：唯一，可为空（L534, L772）
- `caretakerId`
- `kind`：宠物、坐骑、改造体
- `sizeClass` 和 `cmdCost`：1/2/3/2/4/6（L558–565）
- `deployState`：随行、驻守岗位、设施内休息、在途、失联、应急
- `trainingRecord`、`stability`（改造体）、`retainedAbilities` 和方案种子（改造体）
- `popState`：只用于感染体，取值为自由、被约束、受控（L1229）

**不变量和校验：**

1. 每个控制者：随行单位数 ≤ 3；随行占用点数之和 ≤ max(驯兽预算, 生化控制预算)（L567，**取较大值，不相加**）。
2. 种类资格分开检查：驯兽不能控制丧尸，生化控制不能驯服动物（L567, L1243）；改造体按阶段有保有总量和种类上限（L1153–1162）。
3. **校验时机：** 每次部署变化、体型或能力变化（L573）、**读档后先恢复身份再校验预算**（L1251）。超出预算时进入 `overbudget` 状态，强制非主动并提示玩家，**不删除、不杀死**。
4. **交接用两阶段提交：** 发起 → 双方资格、范围、预算检查 → 一个原子事件同时改写 controllerId。永远不会出现两个有效控制者（A75, A89）。
5. **骑乘：** 人和坐骑是两个实体，用附着约束连接；命中按部位结算到具体实体（L546）；上下坐骑有动作硬直和冷却，防止取消攻击后摇（L548）。
6. **载具复用"座位与角色"抽象**（司机、炮手，L501），但载具不是 Companion（L57），没有指挥点、亲密和训练。
7. **控制者死亡或玩家观战：** 失去作战输入，进入预设应急策略；接管时重新走交接校验（L1223, A76）。

**容易遗漏的边界：** 玩家处于 STASHED 状态或已死亡时，宠物不能跟着冻结或消失（L552），应回营并持续产生维护消耗。一个已死亡玩家的组织席位、领袖任务和预留物资，按 L445 的规则释放或继承。

## 10. 有限弹药与物品唯一性

**物品模型【工】：**

- **唯一实例物品：** 武器、书、弹匣、改造核心等。
- **堆叠物品：** 有 `stackId`、类型、数量、批次。拆分会产生新的 stackId，合并要求同类型同批次。
- **每个物品或堆叠恰好有一个位置：** 容器加槽位、世界坐标、实体装备槽、载具弹药箱、武器弹匣或枪膛。"移动"是唯一的事务操作。

**审计不变量：** 按类型，`创建量 − 消耗量 == 现存量`。

- 创建来源只有：世界生成、懒加载的战利品、制作、拆解返还（只返还实际存在的部件，L499）。
- 测试和调试版本每个游戏日跑一次全局审计。

**弹药专项：**

- 弹药流转链：公共仓储 → 搬运中 → 弹箱或弹匣 → 枪膛 → 消耗（L511）。
- 开火命令由服务器检查枪膛余量并扣减，客户端预测只做表现。
- **装填按发提交**，中断时数量精确。也可以选择"整次装填在结束时一次性提交"，两种必须二选一并写清楚。
- 远处 NPC 的抽象战斗同样扣弹药；自动炮台和车载武器从实际供弹容器取弹（A33–A34）。
- 能量、生化载荷、热量、耐久分别记账，冷却不等于补充弹药（L513）。

**懒加载战利品：** 容器第一次被任何人（包括远处 NPC）观察时，用稳定种子生成内容并立即持久化。主线必需品（L140）在世界生成阶段确定性放置，并校验可达性；岛屿化之后由 A68 要求的替代生存链兜底。

**存储增长（D14）：**

- NPC 遗物有物品时永不删除（L740）。
- 丧尸尸体的保留或腐烂策略没有定义。每天击杀可能上万只，必须定义，比如"尸体腐烂，携带物品转入地面堆"。
- 已死 NPC 的身份记录永久保留，数量不大，可以接受。

## 11. 存档

**推荐【工】：** 主机或服务器用 SQLite（WAL 模式）。理由：

- 原生支持事务，多张表可以在一次原子提交里修改，正好对应"唯一事件"。
- 全平台原生可用。

**存档内容：**

- `manifest`：种子、世界生成版本、规则数据版本、日编号、两套人口账本
- `chunk_delta`：地形差量、结构、地面物品
- `entities`：NPC、Companion、个体丧尸、遗物、载具、建筑
- `cohorts`：丧尸群体记录
- `ledger_days`：日结算幂等记录
- `deaths`：同时写入独立的死亡登记表
- `pending_events`：灾害阶段、制作进度、施工进度、改造进度
- `event_log`：用于重放和审计，定期压缩

**其他要点：**

- 世界时间只按模拟 tick 推进，与现实时间无关（L762, A14）。
- 规则数据用稳定 ID 和版本号，跨版本读档要有迁移脚本（L1017）。
- 中断类流程（制作、施工、改造）按"已投入 / 已消耗 / 可释放"三类保存（L337, L1180, A17, A79）。
- 浏览器端的单人存档（SQLite wasm 加 OPFS）复杂度高，建议先不支持浏览器单人（D19）。

## 12. 游戏内研究路线的数据面

- **知识是非物品状态：** 个人知识和技能（L312），以及组织研究记录（L1042）。
- **书和资料是唯一实例物品。** 同一本书对同一个人只给一次主要学习收益，用"个人 × 书籍知识"标记实现（L314）。
- **共享：** 只能通过教学（消耗双方时间）、交易、合作，或转移资料物品实现。不允许全局解锁（A40）。
- **待决（D17）：** 能否用纸张等材料"抄写"出新书？如果能，知识可以复制，但书这个物品本身仍然唯一。
- **研发过程** 拆分为：发现 → 分析 → 前置条件 → 投入 → 得到成果 → 制造（L1040），每一步都是可持久化的进度实体。

## 13. 实施阶段建议

GDD 把人口规模验证放在 M2（L839, L843），但它决定了核心语言、数据结构和地图尺寸。建议**在 M0 之前或与 M0 并行**做无界面的技术验证：

| 验证 | 目标 | 过关标准 |
|---|---|---|
| S1 核心骨架 | 命令/事件/预写日志/快照、不变量审计、确定性重放 | 随机断电测试100次，账本和物品无一偏差 |
| S2 规模验证（最高风险） | 无界面跑100游戏日：101万丧尸、1万 NPC LOD2 | 记录内存、单日结算时间、群体迁移成本；两套账本始终守恒 |
| S3 声学 | 路径衰减、跨层级必听 | 暴力遍历对照零差异 |
| S4 地形与导航 | 积水退水、陆桥断裂成岛、版本失效通知 | A46、A50、A51 无界面通过 |
| S5 NPC 规划器 | 认知隔离接口、HTN、LOD 切换 | A30–A32 场景通过 |
| S6 网络 | ENet 和 WebSocket 双传输、4人、席位状态机、断线和崩溃 | A12、A13、A22、A52 |
| S7 客户端 | Godot 等距渲染、目标手机帧率基线 | 记录具体机型数据（L823） |

之后按 GDD 的 M0–M4 推进。M1 的4名 NPC 必须使用**正式的规划器和正式的 LOD 代码**，不能写专用脚本，否则 M2 会推倒重来（L843 已禁止拿脚本冒充）。和 GDD 一样，这里不给出工期承诺。
